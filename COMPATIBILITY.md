# Compatibility

## Rust

The supported Rust is the latest stable minus two minor versions. `rust-toolchain.toml` pins the exact toolchain the project builds with, currently 1.99.1, and rustup installs it on the first `cargo` call. Nothing older than the pinned toolchain has been tested, so the crates carry no `rust-version` field; one arrives together with a CI job that builds on the oldest supported version.

## Lighthouse

The text between the markers is generated from `overlay_bn::compat` by `UPDATE_COMPATIBILITY_MD=1 cargo test -p overlay-bn compatibility_md_matches_the_constant`; the same test fails when it is stale.

Supported: Lighthouse v8.2.2 through v8.3.2, last verified 2026-11-04. The range is exactly the versions the compatibility matrix has passed and grows only with a matrix run. The workspace is built against v8.3.2: the tag the root `Cargo.toml` pins for `lighthouse_network` and `types`, and the `sigp/rust-libp2p` revision that tag pins, which the root `Cargo.toml` copies. A beacon node above the range is reported `untested` and one below it `unsupported`, on every connect, in the log and in `overlay_bn_compat{state}`; the sidecar keeps running either way.

The design leans on, or works around, fifteen Lighthouse behaviours that no specification promises. Each has a named test, so a release that changes one fails the matrix by name instead of degrading the fleet quietly. Tests marked matrix need a real beacon node and run in the nightly matrix; those marked `--gloas` need the devnet `scripts/lighthouse-matrix.sh <version> --gloas` brings up, with Gloas active from genesis, which runs locally only: it needs Docker and Kurtosis and takes the better part of an hour, so the nightly stays on Sepolia at genesis. The others run on every pull request against `FakeBn`.

| The beacon node's message id equals the sidecar's for the same topic and payload | `published_message_id_matches_fake_bn_for_random_payloads` |

| A parent lookup for a gossip block is seeded with the block's sender and nobody else, a `ResourceUnavailable` answer is re-requested from that peer at once, and the fourth failure drops the lookup and the block. | From v8.3.0 the beacon node still accepts `--libp2p-addresses` but never dials it (`sigp/lighthouse#10229`), so on those releases `add_peer` registration alone admits the sidecar. The env file keeps the flag while the supported range includes a v8.2 release (MD-01 amended) | `matrix_bn_dials_the_listening_sidecar_when_its_inbound_cap_is_full` (matrix), which on v8.3.0 and later passes through `add_peer` alone; the flag still being accepted: `matrix_bn_startup_flags_dial_the_listening_sidecar` (matrix) |
| With gossipsub partial messages on for every `data_column_sidecar_*` topic, the default from v8.3.0 (`--enable-partial-columns`), the beacon node still hands its explicit peer a full message for every column its `data_column_sidecar` event reports. On a chain where no full column travels on gossip at all, because every node has the blobs in its execution layer and sends partials, a column merged from partials or completed from `getBlobs` is published whole (`gossip_methods.rs:1343-1366`), and `publish` leaves out only the peers that asked for partials (`behaviour.rs:676-689` at the pinned rust-libp2p). The sidecar never asks for them. Measured on v8.3.2, 2026-11-12: every column the node reported was forwarded, 768 of 768 over 6 blocks in a 16-slot window, and so were the columns of the other blocks in the window, which the node merged from partials and reported no event for (next row but one) | `matrix_the_node_forwards_full_columns_to_its_explicit_peer_with_partials_on` (matrix, `--gloas`, local only) |
| From the Gloas fork a block whose parent the node has imported but whose parent's payload envelope it lacks is `ParentUnknown` to gossip verification (`fork_choice.rs:1663-1679`, `block_verification.rs:1516-1521`), and the lookup it opens is seeded with the block's sender alone. The lookup starts with the parent block, which the node already holds, so what reaches the sidecar is `beacon_blocks_by_root`, refused four times, and `execution_payload_envelopes_by_root` is never asked for: the lookup and the block are dropped for too many attempts, as in the row above. D42 does not cover this case, since it checks the parent block and not its payload; D44 does, keeping such a block back until the node's `execution_payload` event names the payload its bid builds on. That event fires at import, which is when the child stops being `ParentUnknown`, and `execution_payload_gossip` fires at gossip verification before it. Measured on v8.3.2, 2026-11-12: 4 block refusals, 0 envelope refusals, the child dropped. Measured on v8.3.2, 2026-11-13: the import event fired for every envelope the node verified, 61 of 61 in two runs, own and gossiped, 0.4 to 2.1 s after the gossip event, and for the same 61 on a node whose envelopes came from its sidecar and the beacon API; 8 of the 61 fired it twice. v8.2.2 accepts the topic | `matrix_a_block_whose_parent_envelope_the_node_lacks` (matrix, `--gloas`, local only), which counts both refusals on the sidecar, reads the child's `block` event and `sync_lookups_dropped_total` on the node, and asks the shipped check about the child before and after the payload is imported; `matrix_execution_payload_fires_at_import_for_every_envelope` for the event |
| `execution_payload_gossip` fires once per payload envelope on the first observation from any source, the node's own publish included (`gossip_verified_envelope.rs:297-327`), so a slot's repair deadline starts whether the envelope came by gossip or from the node's own validator client (MD-09 as corrected). Measured on v8.3.2, 2026-11-12: one event for each gossiped and each own envelope, none for any other root | `matrix_execution_payload_gossip_fires_once_per_envelope_from_any_source` (matrix, `--gloas`, local only) |
| Each Gloas message kind the node gossips crosses the overlay and is accepted by a node whose only gossip peer is its sidecar: the payload envelope, payload attestations and proposer preferences, with no REJECT and no invalid message on any of the four topics. Bids are unmeasured: a devnet that self-builds every payload gossips none. Measured on v8.3.2, 2026-11-12 | `matrix_every_gloas_kind_crosses_the_overlay` (matrix, `--gloas`, local only), off the far node's gossipsub counters and its sidecar's `first_arrival` lines |
| MD-09's premise, that column repair anchored on the envelope asks for nothing on a healthy Gloas chain, under one slot in a hundred. Measured on v8.3.2, 2026-11-12, it does not hold on the devnet, for two reasons. The node fires `data_column_sidecar` for the columns it builds from the blobs its own validator client posts, 260 ms to 1.2 s after the envelope on the 4-vCPU VM, so 8 of 10 own proposals were still short at the shipped 250 ms `repair_deadline_ms`. For another node's block it fired nothing in the window: with partial messages on, those columns reach it as partials and from its execution layer, and whichever path completed them registered no event, so the tracker counts all of that block's columns as missing for good and repair would ask for every one of them. MD-06 counted partial-message merges among the event's sources; on this devnet at v8.3.2 no event came that way. Since D43 the sidecar also counts a column the node forwards on its link, which the row three above measures complete, and starts a Gloas slot's deadline 1.5 s after the envelope. Measured on v8.3.2, 2026-11-13, nine runs of 32 slots: all 128 columns of every block forwarded, the last a median 804 ms after the envelope, 1539 ms at the 99th percentile and 1711 ms at the worst of 285 blocks; with the change, 0 of 94 slots late in three runs, and neither shipped sidecar on the devnet made a repair request. The second writer stays until a Lighthouse release fires `data_column_sidecar` for a column merged from partials or completed from `getBlobs` under Gloas; none does yet and the report upstream is not filed. Unmeasured on production hardware | `matrix_column_repair_is_quiet_on_a_healthy_gloas_chain` (matrix, `--gloas`, local only), which feeds the tracker the node's events and what it forwards, and prints each block's lag |
| A block the node fetches by root fires `block` and no `block_gossip`. The event is registered in one place, `GossipVerifiedBlock::new` (`block_verification.rs:1116-1124`), which a gossip block and a block published over the beacon API both go through; a lookup hands `process_block` a `LookupBlock` (`sync_methods.rs:112-180`, `block_verification.rs:1433-1458`) and builds none. So a block imported through a lookup opens no custody entry and gets no column repair, and `block` is the one event that names every import, which is why the parent check reads it (D42). Measured on v8.3.2, 2026-11-12, on a node whose only peer is its sidecar: with inject off for one slot the node missed block N, fetched it from the sidecar's by-root cache 50 to 140 ms into slot N+1, and fired `block` for it and no `block_gossip` in the three slots after, in four runs of four. The node ran with `--unknown-root-min-peers 1`. At the default of 3, a root that only the sidecar's messages have named opens no lookup at all, and the node stayed a block behind until the block was posted to its beacon API | `matrix_block_gossip_does_not_fire_for_a_block_fetched_by_root` (matrix, `--gloas` with `GLOAS_BY_ROOT=1`, local only), which also requires a by-root hit on the sidecar and the node's own `Processing Lookup block` line for the root |

The sidecar is a standard gossipsub peer. Other consensus clients' trusted-peer features are untested and nothing here claims to support them.

## Platforms

Release binaries are built for Linux on x86_64 and aarch64. macOS builds the workspace and runs the test suite, for development only; Linux-only code sits behind `cfg(target_os = "linux")` and the sidecar is not supported on macOS in production.
