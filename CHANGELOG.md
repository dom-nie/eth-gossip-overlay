# Changelog

Everything worth telling an operator about, newest first. The format is [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the version numbers are [semantic](https://semver.org/spec/v2.0.0.html).

Every section also carries a `Protocol:` line, because the number that decides how an upgrade goes is not the one on the tarball. The protocol major travels in the overlay's ALPN and the minor and the feature bits in `HELLO`, so a release that only adds a feature bit pairs with every older host and can be rolled out in any order, and a major bump splits the fleet into two overlays until the last host is done. [docs/upgrading.md](docs/upgrading.md) is the procedure for both cases and [CONTRIBUTING.md](CONTRIBUTING.md) has the line's grammar.

## [Unreleased]

Protocol: major unchanged (1); features added: DATAGRAM_BATCHES (bit 0), STRIPING (bit 1), REPAIR (bit 2)

The first release, so all of it is new.

### Added

- `eth-gossip-overlay`, a sidecar for a Lighthouse beacon node. It joins a QUIC mesh of the other sidecars you run and hands each beacon node the blocks, blobs and data columns another of your nodes has already validated, instead of leaving it to wait for the public gossip mesh. The beacon node keeps its public peers throughout and validates everything the sidecar injects, so a fleet with the overlay down is a fleet without the overlay.
- Admission by a key rather than a certificate. Every host derives its overlay TLS key from one fleet seed and its own hostname, so the roster is the whole membership list and there is nothing to issue or renew. `eth-gossip-overlay gen-seed` writes the seed, and a second seed can be in force alongside it, which is what makes rotating one a rolling change rather than an outage.
- Version negotiation built for a fleet that is upgraded host by host: the protocol major in the ALPN, the minor, the feature bits and the frame limits in `HELLO`, and a pair that runs at the lower minor and the intersection of the bits.
- The beacon node link: the sidecar dials the node, registers itself as a trusted peer on every reconnect so the node dials back, mirrors whatever the node is subscribed to including every data-column topic per fork digest, injects under a rate limit and a kill switch, and answers the handful of req/resp methods a well-behaved peer has to answer.
- Lighthouse v8.2.2, with the version checked at every connect and reported in `overlay_bn_compat`, and a nightly matrix that runs the assumptions against a real beacon node. A Lighthouse identity is always a secp256k1 key, so the sidecar is built to verify one; it still signs with ed25519 itself.
- Deduplication in both directions from one seen cache, keyed by the consensus message id computed off the compressed payload, so nothing the local node has already seen is injected and nothing arriving twice is forwarded twice.
- A full mesh that repairs itself: one connection per pair, a reconnect with jittered backoff, a superseding handshake that tells a restarted peer from a moved one, and per-peer send queues bounded by bytes and by age so a slow peer costs its own lane and nothing else.
- Routing by subscription: a message goes only to the peers whose beacon node wants its topic, over 16-bit topic ids exchanged at connect and extended as the local subscriptions change.
- Attestations and the rest of the small class travel batched, over unreliable QUIC datagrams: everything a host has for one peer inside `classes.small.batch_window_ms` leaves in one datagram instead of a stream per message, and anything older than `classes.small.stale_after_ms` is dropped rather than delivered late, because an attestation that misses its slot costs the beacon node work and buys it nothing. A batch the path turns out not to carry, and any payload too big for one, falls back to a stream. A peer that has not taken this release is sent whole messages on streams as it always was, so the fleet can be upgraded host by host.
- Small-class batches cross the WAN through a few hosts of the region they are for, not one copy per subscriber. Each origin picks its own relays from a hash of its own hostname over that region's live hosts, so the load lands on all of them and nothing has to be agreed; a relay delivers the batch to its region and publishes only what its own beacon node asked for. A remote region with fewer than `overlay.fanout.small.relay_min_remote_hosts` live subscribed hosts is sent to directly, because the copies saved there do not pay for the extra in-region hop, and `overlay.fanout.small.cross_region: direct` turns relaying off altogether. On a fleet of two regions of a hundred, this is about thirty times less WAN traffic for the small class, for a few milliseconds added to an attestation that has eight seconds to spare.
- Blocks and data columns are split into 2 KB chunks with Reed-Solomon parity and spread over the subscribed hosts of each region, one chunk per host, and every host passes the chunk it was sent to the rest of its own region the moment it arrives. The origin's outgoing traffic for a block is about two block-equivalents whatever the fleet size, instead of one copy per host, and the second hop never crosses the WAN. Each host collects the chunks it is sent, puts the message back together as soon as it holds enough of them, and injects it into its own beacon node once; the parity chunks mean a host that is down or a chunk that is lost costs nothing, and `overlay_parity_used_total` says how often that happened. A region with fewer live subscribers than `overlay.fanout.large.stripe_min_recipients` still takes whole messages, `overlay.fanout.large.in_region: direct` keeps the origin's own region on that path, and a host that has not taken this release is sent whole messages too, so the fleet can be upgraded host by host.
- Prometheus metrics on `:7789`, one structured log stream on stdout, and an event log for large messages.
- Import-time telemetry, so you can see the bottleneck the overlay cannot fix. The sidecar subscribes to the beacon node's block event stream and logs an `import` line for every block the node imports, carrying the milliseconds between the block reaching this host and the node finishing with it, or saying the block never reached this host at all. `newPayload` and column verification take 200 to 500 ms on a full block, and every 100 ms of that cancels 100 ms of whatever the overlay won, so this is where you see how much of the gain is being spent after the race is already over. Each line names the block by the same root the `first_arrival` line uses, so the two join without a second identifier. `overlay_bn_events_connected` and `overlay_import_events_total` are the same numbers as metrics, and a beacon node whose event API is off is logged once and left alone rather than retried.
- `eth-gossip-overlayctl`, over a local admin socket: `status` prints the kill switch, the beacon node and one row per live peer with the software version and the features that pair negotiated, `inject` flips the kill switch, and `roster reload` re-reads the files. `SIGHUP` does the same reload, without dropping a connection, and a `roster.yaml` your discovery tool rewrites is picked up on its own within 10 seconds, so dynamic membership needs no interface beyond the file. An automatic reload that would drop more than half the fleet is refused and counted, on the grounds that a truncated file is likelier than half a fleet leaving; `roster reload` applies it anyway.
- `eth-gossip-overlay check-config`, which reads the same files a start reads and says who this host is and what it would hold, and `eth-gossip-overlay peer-id`, which prints the id the beacon node has to trust before the sidecar has ever run.
- Deployment examples in `deploy/`: a systemd unit with readiness, a watchdog and the credential the seed arrives through, the sysctl drop-in, an nftables allowlist and the Ansible templates for the roster and the host name.
- A container image with the two binaries, a libc and a non-root user, and a compose demo in `examples/compose/` that runs three sidecars and three beacon nodes on one machine.
- Ten Prometheus alert rules and a Grafana dashboard in `deploy/`, and `docs/rollout.md`, which is how to get the sidecar onto a fleet without guessing whether it helped: a canary against a control group running the same code with injection off, the three numbers that decide it and the exact queries for them, and a rollback that is one command and needs no restart. Every alert links to a section of `docs/troubleshooting.md` saying what it means and what to look at first.
- Operator documentation in `docs/`, written for someone who runs beacon nodes and has never seen this project: a quickstart that goes from a downloaded binary to a message that arrived over the overlay, the beacon node's side of it, a configuration reference generated from the code so it cannot drift, the threat model and the seed-rotation procedure, and a runbook split between the alerts and the symptoms nothing alerts on.
- Tagged releases: Linux x86_64 and aarch64 tarballs with the binaries, the licence and `deploy/`, a `SHA256SUMS`, a provenance attestation, a published image, and release notes taken from this file.
- Transport tuning for a network you run end to end, and one table saying where the memory goes. Every connection opens at `overlay.initial_window_bytes` instead of the RFC's 14 kB, so a link that carries one block every 12 s is not paying several round trips per block to leave slow start. Inbound, one peer may hold 64 unidirectional streams, 4 bidirectional and 1 MiB per stream, and a connection receive window worked out from your roster size and the memory ceiling, so no peer and no fleet size can push the process past what it was sized for. A socket buffer the kernel quietly capped now says so and names the sysctl to raise. The unit sets `MemoryMax=1G`, which is what that table adds up to at a 200-host roster with a quarter left spare; the sidecar prints the same table at startup and from `check-config` at your own roster size, and warns if it does not fit. [docs/performance.md](docs/performance.md) has the memory table, generated from the code so it cannot drift, and the throughput numbers with the command that reproduces them.
- Every block and data column a host takes is kept whole for a minute, so that when gap repair ships a sidecar can hand a sibling the chunks it lost instead of leaving it to wait for the public mesh. Nothing asks for them yet and nothing is announced. It costs 26 MiB of the memory table, which comes out of the derived connection receive window rather than the ceiling: at a 200-host roster each connection now gets 2.79 MiB instead of 2.92, and the largest roster that fits under `MemoryMax=1G` is 477 hosts rather than 497.
- The sidecar reads the header of every block and data column it takes, and nothing else inside a gossip payload: a block's slot and root, and a column's slot, index and block root. Column headers are read without touching the 40 KB of cells behind them. The block and column each go into the recent store under the identity their own bytes carry, which is what a sibling will name a column by when gap repair for custody columns lands. Nothing acts on those numbers yet beyond that index and the arrival log line.
- `first_arrival` lines for blocks and data columns now carry `slot` and `block_root`, so a block can be followed across the fleet by its consensus name and not only by its gossipsub id. The keys are absent on a line that had no header to read, as `null` was never written for a missing field. Existing queries join on `msg_id` and are unaffected; [docs/events.md](docs/events.md) has the schema.
- Gap repair for chunks. A host still missing pieces of a block or a column `classes.large.repair_deadline_ms` after the first chunk arrived asks a sibling that already sent it one for exactly the pieces it is short of, and gets them back on the same stream. It asks the in-region hosts that passed it a chunk first, by round trip, then the host the message came from; each attempt waits four round trips, between 100 and 500 ms, and after three peers or 1.5 seconds it stops and lets public gossip deliver. That covers the case parity cannot: a host that was a stripe target when the block was cut up and stopped talking to its region before its chunks were passed on. Repaired chunks are never forwarded again, so a repair costs one exchange and not a second fan-out. `overlay_repair_requests_total{outcome}` says whether repair is working or only running, and `OverlayRepairRateRising` fires above 0.1 requests per second per host, a threshold [docs/rollout.md](docs/rollout.md) derives. The deadline reloads on SIGHUP, because 250 ms is an estimate a canary should replace. A host that has not taken this release is never asked and never has to answer, so the fleet can be upgraded host by host.
- Optional and off unless you ask for it: `bn.by_root_cache.enabled` lets the sidecar answer its own beacon node's `BeaconBlocksByRoot` and `DataColumnSidecarsByRoot` lookups out of the blocks and columns it is already holding, so a missing-parent recovery that happens to ask the sidecar is a localhost round trip instead of a request to the public network. Lighthouse does not prefer trusted peers when it picks who to ask, so how often that happens is yours to measure: `overlay_by_root_requests_total{protocol,outcome}` counts every lookup as a hit or a miss, and a miss is refused exactly as it was before, so a lookup that lands here and finds nothing costs the node nothing. It widens the recent store to `bn.by_root_cache.slots` slots, 16 by default, which is 57 MiB on top of the 26 the store already holds; that comes out of the derived connection receive window rather than the ceiling, taking a 200-host roster from 2.79 MiB per connection to 2.50. The flag reloads on SIGHUP, so you can turn it off without restarting, and [docs/performance.md](docs/performance.md) has the per-slot arithmetic before you turn it on. The inject kill switch refuses these lookups too, so `inject: false` stops everything the sidecar hands its node.
- Gap repair for custody columns. A beacon node needs half the columns of a block before it can reconstruct the rest and import, so a host whose node is still short of one `classes.large.repair_deadline_ms` after it accepted the block asks its region for that column by name, in round-trip order, and hands it over. Columns the overlay is already delivering in pieces are left to chunk repair; the rest are asked for lowest index first, and only as many as the node needs to reach the half, because past that it can work out the remainder itself. Every fact behind that decision comes from the beacon node's own event stream: which block it accepted, which columns it has verified and which subnets it custodies. Nothing a sibling sends can change what this host asks for or what it will answer with, which is what makes a forged column sent by a roster peer cost that peer's own bytes and nothing else. `overlay_repair_requests_total` now carries `form="chunk"` or `form="column"`, and `docs/troubleshooting.md` splits the runbook the same way. `classes.large.column_repair: false` and a SIGHUP turn it off without a restart, and a host that has not taken this release is never asked and never has to answer.
- A column a host obtained by repair is no longer served onward: it is handed to the beacon node and read for the event line, never kept, so a forged column that one host was talked into accepting stops at that host. `overlay_column_index_conflict_total`, two payloads claiming one column, now alerts as `OverlayColumnIndexConflict`, and the warn line beside it names the held and the refused message ids so the peer behind it can be found and taken out of the roster.
- Optional, Linux only and off unless you ask for it: `overlay.io_thread.pin_cpu` names a reserved core, and the QUIC endpoint then runs on a single-threaded runtime of its own pinned to it, so a block arriving from a sibling is read by a thread that was waiting for it instead of queueing behind the router or the beacon node link. A core the kernel refuses is a warning and an unpinned overlay, never a failed start. `overlay_io_thread_pinned` says which you got, and [docs/performance.md](docs/performance.md) says when it is worth setting and how to check with `ps -L -o psr`.
- On a host with a reserved core and kernel 6.13 or later, `overlay.io_thread.prefer_busy_poll` makes that core spin on the overlay's queue for `busy_poll_usecs` before it sleeps, and masks the NIC queue's interrupt for `irq_suspend_timeout_ms` at a time while packets keep arriving. A block from a sibling is then read by a core that was already looking, with no interrupt between the wire and the reader, and between bursts the queue goes back to interrupts so nothing is burned while the fleet is quiet. Masking the interrupt is set over netdev netlink and needs `CAP_NET_ADMIN`, which the unit can grant with `AmbientCapabilities=`; `irq_suspend_timeout_ms: 0` takes the busy polling without it. An older kernel, a missing capability or a device with no NAPI queue each cost one info line and leave `overlay_busy_poll_enabled` at 0, and never a failed start. [docs/performance.md](docs/performance.md) has the `ethtool -S` check that says whether the interrupts really stopped.
- `overlay.io_thread.steering` puts the overlay's own UDP traffic on a NIC receive queue of its own and pins that queue's interrupt to the core you reserved, so signature verification on the beacon node's cores never contends with fan-out. `auto` asks the card for a flow rule and falls back to the kernel's receive flow steering where the card has none; `ntuple` and `rfs` name one or the other. Run `eth-gossip-overlay steering plan` first: it prints exactly what would be changed on this host and changes nothing, and [docs/performance.md](docs/performance.md) shows the output for a card of each kind. A step the card refuses is a warning and the rest of the plan still runs, which `overlay_steering_applied{action}` reports one series at a time, and everything is put back at a clean shutdown so a flow rule never outlives the process that made it. Off unless you set it, and it needs `ethtool` and `CAP_NET_ADMIN`.
- A peer may bind at most 1024 topic ids, the same count its HELLO may announce, and a peer that binds one more is disconnected; the memory budget on the startup line and in `docs/performance.md` carries every peer's table at that cap as `peer_topic_tables`.
- Repair answers are rate limited per peer, three attempts per message times the large-class rate the beacon node limiter admits, 900 a second at the defaults, and a request that names data chunks alone is served from the stored payload without running the codec. A request past the limit is answered as not found and shows as `overlay_repair_requests_total` with `outcome="rate_limited"`, which reads zero on an honest fleet.

### Changed

- The wire changed with the name. The ALPN is `eth-gossip-overlay/1`, the SNI the dialler sends is `eth-gossip-overlay`, and every host's overlay TLS key is derived under the salt `eth-gossip-overlay/v1`, so the key a given seed and hostname produce is a different key than before. A host built before this cannot pair with one built after: the ALPN alone fails the handshake, and the pin tables would disagree even if it did not. Nothing is released yet, so no fleet is mixed today; the same change after a tag would be a flag day and a protocol major bump.
- The binaries are `eth-gossip-overlay` and `eth-gossip-overlayctl`, and everything named after them moved with them: the unit is `eth-gossip-overlay.service`, the directories are `/etc/eth-gossip-overlay`, `/var/lib/eth-gossip-overlay` and `/run/eth-gossip-overlay`, and the environment variables are `ETH_GOSSIP_OVERLAY_*`, including the `ETH_GOSSIP_OVERLAY_TRUSTED_PEER_ARGS` the beacon node's drop-in reads. If you are running a build from `main`, rename the unit and the directories, update the drop-in, and re-point your scrape job: the shipped rules and dashboard now select `job="eth-gossip-overlay"` and `unit="eth-gossip-overlay.service"`.
- `classes.small.batch_window_ms` and `classes.small.stale_after_ms` reload on SIGHUP, so retuning the batch window or the age at which a batch is given up on no longer costs a restart.
- `overlay.fanout.small.cross_region`, `overlay.fanout.small.relays_per_remote_region` and `overlay.fanout.small.relay_min_remote_hosts` reload on SIGHUP too, so turning relaying off, or retuning how many hosts carry a region's batches, no longer costs a restart.
- `overlay.fanout.large.stripe_min_recipients` reloads on SIGHUP as well, so the number of subscribers a region needs before large messages are striped across it rather than sent whole can be moved while the fleet runs. The other two keys beside it still need a restart.
- `overlay.fanout.small.in_region` is gone. Striping is what the key chose between and the small class is whole payloads batched together, so `direct` was the only value it could ever have taken. Remove the line if your `config.yaml` carries it; the file is parsed strictly and an unknown key stops a start.
- The `ts_source` field on `first_arrival` lines and the `overlay_hw_timestamps` gauge are gone. The field said `sw` and the gauge read 0 on every host, because arrival times were never read off a NIC, and they will not be: quinn's socket has no room for the kernel's timestamp control message, and once quinn has turned datagrams into stream bytes there is no message a per-datagram stamp could be attached to. A Loki query that selected on `ts_source` was selecting every line and can drop the term; [docs/events.md](docs/events.md) has the schema.
- The sidecar no longer claims custody of any column subnet to its beacon node. It answers MetaData v2, which carries no custody group count, so the node does not count it as a custody peer when it looks for peers on a sampling subnet or picks whom to ask for a column. The by-root cache therefore serves blocks only: Lighthouse asks custody peers alone for `DataColumnSidecarsByRoot`, so that handler is never reached, while `BeaconBlocksByRoot` lookups land on it as before.
